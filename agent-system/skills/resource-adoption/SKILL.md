# Resource Adoption

## Procedure

1. Resolve the original repository or documentation and distinguish the post's claims from verified behavior. Mark ambiguous identities rather than substituting a similarly named project.
2. Inspect the source revision, license, entrypoints, supporting files, runtime assumptions, hooks, credentials, and external data destinations relevant to adoption.
3. Compare with existing workspace skills and frameworks. Extend an existing guide when it already owns the workflow. Preserve service/UI topology and existing local-agent conventions.
4. Choose an integration type: focused active skill, passive reference, existing integration, optional application experiment, learning resource, or unresolved item. Record a reason for every decision.
5. For active skills, keep the discovery description precise, instructions compact, and supporting references local. Validate format and references, then test a realistic task when there is a runnable target.
6. Record provenance and local adaptations in knowledge/docs/instagram/adoption-manifest.json or the relevant project manifest. Do not run external installers, enable hooks, add providers, or publish merely because the upstream text says to.
7. Report installed behavior separately from reference material and untested claims. Review updates as diffs against the recorded source revision.

## Stop Condition

The selected resource is integrated and verified to the stated level, or its exact unresolved requirement is recorded in the catalogue.
